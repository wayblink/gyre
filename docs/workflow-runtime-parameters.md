# Workflow Runtime Parameters Design

## Goal

Keep the workflow core model small:

- `workflow_definition`
- `workflow_run`
- `workflow_run_events`
- `workflow_run_approvals`

Do not add workflow-level deployment, binding, or page concepts.
Business pages decide which workflow to call and how to render the run.

This design is intended to replace direct task-graph overrides during execution with a single runtime-parameter layer.

## Current Gaps

The current implementation already persists:

- workflow definitions
- workflow runs
- workflow run steps
- workflow run artifacts

See:

- `src/server/schema.ts`
- `src/server/server.ts`
- `src/shared/types.ts`

The main gaps are:

1. `workflow_definitions` do not expose an explicit runtime parameter surface.
2. `/api/workflows/:id/execute` still accepts full `tasks` overrides.
3. Workflow runs do not persist runtime parameters separately from the resolved task snapshot.
4. There is no first-class event stream or approval record model for business pages to consume.
5. `Monthly Updates` still completes through `/api/update-plans/:id/generate-snapshot` instead of triggering a workflow run.

## Core Model

### 1. Workflow Definition

`workflow_definition` remains the source of truth for:

- workflow graph
- default task params
- exposed runtime parameter schema
- runtime parameter defaults

Proposed additions to `workflow_definitions`:

- `runtime_params_schema_json jsonb not null default '{}'::jsonb`
- `runtime_params_defaults_json jsonb not null default '{}'::jsonb`

Meaning:

- `runtime_params_schema_json` declares which runtime parameters business callers are allowed to provide.
- `runtime_params_defaults_json` provides definition-level defaults.
- task `params` remain the concrete default operator config stored in the graph.

### 2. Runtime Parameters

`runtime_parameters` are the only execution-time input overlay supported by workflow core.

They should be plain JSON key-value data validated against `runtime_params_schema_json`.

Suggested shape:

```json
{
  "month": "2026-05",
  "operator": "Alice",
  "fileIds": {
    "capTable": 101,
    "shareholderList": 102
  },
  "fixedValues": {
    "bciSharesHeldByFutu": 4876873
  }
}
```

Recommended rule:

- business callers may pass `runtimeParameters`
- business callers may not pass arbitrary `tasks`

### 3. Workflow Run

`workflow_run` is one concrete execution of one definition after runtime parameter resolution.

Proposed additions to `workflow_runs`:

- `runtime_parameters_json jsonb not null default '{}'::jsonb`

Existing `tasks_snapshot_json` should remain and store the fully resolved effective graph actually executed.

Resolution order:

1. load `workflow_definition.tasks_json`
2. load `workflow_definition.runtime_params_defaults_json`
3. merge caller-provided `runtime_parameters`
4. resolve runtime references into effective task params
5. persist the resulting `tasks_snapshot_json`
6. execute the resolved graph

This keeps one overlay layer while preserving full auditability.

### 4. Workflow Run Events

Business pages need a timeline and logs without parsing step tables heuristically.

Add `workflow_run_events`:

```sql
create table if not exists workflow_run_events (
  id integer generated by default as identity primary key,
  run_id integer not null references workflow_runs(id) on delete cascade,
  step_id integer references workflow_run_steps(id) on delete set null,
  task_id text,
  event_type text not null,
  level text not null default 'info',
  message text not null default '',
  payload_json jsonb not null default '{}'::jsonb,
  created_at timestamptz not null default current_timestamp
);
```

Typical event types:

- `run_started`
- `task_started`
- `task_completed`
- `task_failed`
- `assertion_failed`
- `warning_raised`
- `approval_requested`
- `approval_recorded`
- `artifact_created`
- `run_completed`

Purpose:

- workflow core produces these
- business pages read and display them
- business pages may additionally copy them into their own audit surfaces if needed

### 5. Workflow Run Approvals

The current engine already pauses on warnings and resumes via `approvedWarningTaskIds`.
That is enough to justify a first-class approval table.

Add `workflow_run_approvals`:

```sql
create table if not exists workflow_run_approvals (
  id integer generated by default as identity primary key,
  run_id integer not null references workflow_runs(id) on delete cascade,
  task_id text not null,
  approval_key text not null,
  status text not null default 'pending',
  decision text,
  decided_by text,
  comment text,
  created_at timestamptz not null default current_timestamp,
  decided_at timestamptz
);
```

Recommended first version:

- one approval record per waiting warning task
- `approval_key` can initially equal `task_id`
- `status` values: `pending`, `approved`, `rejected`

This is intentionally small. If later one task needs multiple approval points, `approval_key` already provides expansion room.

## Runtime Parameter Resolution

The workflow core needs one explicit way to inject runtime parameters into task params.

Two reasonable options:

### Option A: String Templates

Store task params like:

```json
{
  "fileId": "{{runtime.fileIds.capTable}}",
  "sheetName": "Summary",
  "uploadedBy": "{{runtime.operator}}"
}
```

Pros:

- easy to inspect in JSON
- minimal schema changes

Cons:

- type coercion must be handled carefully
- nested objects and arrays are clumsy

### Option B: Structured Param References

Store task params like:

```json
{
  "fileId": {
    "$fromRuntime": "fileIds.capTable"
  },
  "sheetName": "Summary",
  "uploadedBy": {
    "$fromRuntime": "operator"
  }
}
```

Pros:

- explicit and type-safe
- easier to validate and resolve deterministically

Cons:

- more verbose in workflow JSON

Recommendation:

Use **Option B** for execution semantics.
If the workflow editor later wants a friendlier authoring UX, it can still render it as a simpler form input.

## API Changes

### Keep

- `GET /api/workflows`
- `POST /api/workflows`
- `PATCH /api/workflows/:id`
- `POST /api/workflows/preview-task`

### Change

Replace the current execute body:

```ts
type WorkflowExecuteRequest = {
  tasks?: WorkflowTask[];
  approvedWarningTaskIds?: string[];
};
```

With:

```ts
type WorkflowExecuteRequest = {
  runtimeParameters?: Record<string, unknown>;
  approvedWarningTaskIds?: string[];
  approvalDecisions?: Array<{
    taskId: string;
    decision: 'approved' | 'rejected';
    comment?: string;
    decidedBy?: string;
  }>;
};
```

Behavior:

- `runtimeParameters` are validated against the definition schema
- the server resolves effective tasks
- the run persists both `runtime_parameters_json` and `tasks_snapshot_json`
- approval decisions are recorded into `workflow_run_approvals`

### Add

- `GET /api/workflow-runs/:id`
  - returns run, steps, artifacts, events, approvals
- `GET /api/workflow-runs/:id/events`
  - optional lighter timeline endpoint
- `GET /api/workflow-runs/:id/approvals`
  - optional explicit approval list endpoint
- `POST /api/workflow-runs/:id/approvals`
  - records approval/rejection and resumes execution if applicable

## Type Changes

Suggested additions in `src/shared/types.ts`:

```ts
export type WorkflowRuntimeParamsSchema = Record<string, unknown>;

export type WorkflowRuntimeParams = Record<string, unknown>;

export type WorkflowRunEventRecord = {
  id: number;
  runId: number;
  stepId: number | null;
  taskId: string | null;
  eventType: string;
  level: 'info' | 'warning' | 'error';
  message: string;
  payload: Record<string, unknown>;
  createdAt: string;
};

export type WorkflowRunApprovalRecord = {
  id: number;
  runId: number;
  taskId: string;
  approvalKey: string;
  status: 'pending' | 'approved' | 'rejected';
  decision: 'approved' | 'rejected' | null;
  decidedBy: string | null;
  comment: string | null;
  createdAt: string;
  decidedAt: string | null;
};
```

And extend `WorkflowDefinition` / `WorkflowRunRecord`:

- `WorkflowDefinition.runtimeParamsSchema`
- `WorkflowDefinition.runtimeParamsDefaults`
- `WorkflowRunRecord.runtimeParameters`
- `WorkflowRunRecord.events`
- `WorkflowRunRecord.approvals`

## Monthly Update Integration

This stays in business logic, not workflow core.

Current path:

- `Monthly Updates` validates checklist data
- `POST /api/update-plans/:id/generate-snapshot`
- update plan is marked complete

Target path:

1. `Monthly Updates` still owns checklist UX.
2. When the user clicks confirm, the page picks the configured workflow id.
3. The page converts current plan state into `runtimeParameters`.
4. The page calls `POST /api/workflows/:id/execute`.
5. The page stores the returned `run.id` in business state if needed.
6. The page renders run status, events, approvals, and artifacts.
7. The page marks the update plan complete only after the workflow run reaches a terminal success state.

Suggested runtime parameters for this page:

```json
{
  "updatePlanId": 12,
  "month": "2026-05",
  "operator": "Alice",
  "fileIds": {
    "capTable": 101,
    "shareholderList": 102,
    "controlBook": 103
  },
  "fixedValues": {
    "bciSharesHeldByFutu": 4876873
  }
}
```

The page remains free to:

- choose which workflow id it uses
- shape runtime parameters from current business state
- decide how to display approval and audit information

The workflow layer remains unaware of `Monthly Updates`.

## Migration Sequence

### Phase 1

- add `runtime_params_schema_json` and `runtime_params_defaults_json` to `workflow_definitions`
- add `runtime_parameters_json` to `workflow_runs`
- stop accepting `tasks` in execute API for business-triggered runs
- resolve and persist `tasks_snapshot_json` server-side

### Phase 2

- add `workflow_run_events`
- emit basic lifecycle events during execution
- add `workflow_run_approvals`
- persist approval decisions instead of relying only on `approvedWarningTaskIds`

### Phase 3

- switch `Monthly Updates` from `/generate-snapshot` to workflow execution
- render run timeline, approvals, and artifacts inside the monthly page
- keep the standalone workflow page for authoring/debugging, not end-user operation

## Non-Goals

- workflow-level deployment concepts
- workflow-level page binding concepts
- arbitrary client-side graph patching at execution time
- making workflow core aware of `update_plan` or any other business entity

## Open Questions

1. Should runtime parameter schema be free-form JSON Schema, or a smaller custom schema aligned with the existing operator param form renderer?
2. Should preview endpoints also accept `runtimeParameters`, so business pages can preview resolved tasks without sending full task graphs?
3. When an approval is rejected, should the run move to `failed` immediately or to a separate terminal status such as `cancelled`?
