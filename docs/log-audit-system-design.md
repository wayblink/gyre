# 日志与审计系统设计

## 目标

本项目需要两类能力：

1. 日志能力：记录一个操作的执行过程、阶段事件、错误、警告、耗时，便于排查问题和渲染时间线。
2. 审计能力：记录一个操作对业务对象或 Excel 对象造成了什么变化，便于追责、回放、比对 before/after。

关键要求：

- 同一个“操作”发生时，日志和审计必须一起写入数据库。
- 两类记录必须能对得上，不能靠时间模糊匹配。
- workflow 层和业务层都能接入，但不要互相耦合。
- 未来如果接入类似 capmerge 的 Excel 编辑器，需要支持细粒度单元格审计。

## 核心结论

不要把“日志”和“审计”塞进一张表。

建议拆成三层：

1. `operation_records`
   作用：一个顶层操作一行，作为统一关联锚点。
2. `operation_logs`
   作用：这个操作过程中的时间线事件，可以有多行。
3. `audit_logs`
   作用：这个操作对哪些对象造成了什么变更，可以有多行。

其中：

- `operation_records.operation_id` 是全系统相关记录的统一关联 id。
- `operation_logs.operation_id` 和 `audit_logs.operation_id` 都指向同一个顶层操作。
- `workflow_run_events` 保留，但新增 `operation_id` 可选关联字段；这样 workflow 原生事件流和统一日志系统就能对上。

## 为什么需要单独的 `operation_records`

如果只有日志表和审计表，仍然会遇到两个问题：

1. 一个操作可能有很多日志行，也可能有多条审计行，缺少一个稳定“根节点”。
2. 业务页面通常需要“这次操作”的摘要，而不是一堆松散事件。

所以需要一个“操作主表”：

- 谁发起的
- 作用在哪个业务域
- 当前状态
- 关联 month / file / workflow_run / request
- 开始和结束时间

它是“操作会话”，不是明细事件。

## 推荐数据模型

### 1. operation_records

建议新增：

```sql
create table if not exists operation_records (
  id bigint generated by default as identity primary key,
  operation_id uuid not null unique,
  parent_operation_id uuid,
  source_kind text not null,
  domain text not null,
  action text not null,
  status text not null default 'running',
  actor_type text not null default 'user',
  actor_id text,
  actor_name text,
  request_id text,
  month_id integer references months(id) on delete set null,
  file_id integer references product_files(id) on delete set null,
  workflow_run_id integer references workflow_runs(id) on delete set null,
  workflow_step_id integer references workflow_run_steps(id) on delete set null,
  entity_type text,
  entity_id text,
  entity_label text,
  summary text not null default '',
  metadata_json jsonb not null default '{}'::jsonb,
  started_at timestamptz not null default current_timestamp,
  finished_at timestamptz,
  duration_ms integer,
  error_message text
);
```

字段说明：

- `operation_id`：统一关联 id，代码里生成 UUID。
- `parent_operation_id`：可选，用于“月度执行触发了 workflow run，workflow run 又触发了审批/产物回写”这种父子链路。
- `source_kind`：`business` / `workflow` / `excel` / `system`。
- `domain`：`monthly_run` / `summary` / `files` / `workflow` / `holdings` 等。
- `action`：`monthly_run.execute`、`summary.source.set`、`file.upload`、`workbook.cell.update`。
- `summary`：供列表页直接展示的一句话。

### 2. operation_logs

建议新增：

```sql
create table if not exists operation_logs (
  id bigint generated by default as identity primary key,
  operation_id uuid not null,
  seq integer not null,
  level text not null default 'info',
  event_type text not null,
  message text not null default '',
  payload_json jsonb not null default '{}'::jsonb,
  created_at timestamptz not null default current_timestamp,
  unique(operation_id, seq)
);
```

字段说明：

- `seq`：同一个操作内部的事件顺序号，避免只靠时间排序。
- `event_type`：`operation_started`、`workflow_run_created`、`file_uploaded`、`approval_requested`、`operation_completed`、`operation_failed`。
- `payload_json`：补充上下文，比如 month、sheet、warning 内容、SQL 结果摘要。

### 3. audit_logs

建议保留现有表名，但把结构扩展成真正可用的审计表：

```sql
create table if not exists audit_logs (
  id bigint generated by default as identity primary key,
  operation_id uuid not null,
  audit_type text not null,
  actor_type text not null default 'user',
  actor_id text,
  actor_name text,
  domain text not null,
  action text not null,
  entity_type text not null,
  entity_id text,
  entity_label text,
  before_json jsonb,
  after_json jsonb,
  diff_json jsonb,
  metadata_json jsonb not null default '{}'::jsonb,
  created_at timestamptz not null default current_timestamp
);
```

字段说明：

- `audit_type`：
  - `business_state_change`
  - `business_decision`
  - `excel_content_change`
  - `excel_structure_change`
  - `workflow_control_action`
- `before_json` / `after_json`：给业务页面和审计回看用。
- `diff_json`：可选，后续如果要显示高亮 diff 可以直接用。

### 4. workflow_run_events 扩展

保留现有 `workflow_run_events`，新增可空字段：

```sql
alter table workflow_run_events add column if not exists operation_id uuid;
alter table workflow_run_events add column if not exists request_id text;
```

这样 workflow 引擎自己的运行时间线不需要被替换，但可以和统一操作系统挂上钩。

## 统一关联规则

这是最重要的约束：

- 每次顶层业务动作先生成一个 `operation_id`。
- 主业务写入、`operation_logs`、`audit_logs`、`workflow_run_events` 的扩展字段，全部带这个 `operation_id`。
- 所有写入必须在同一个数据库事务里完成。

这样之后任何页面都可以：

- 先查 `operation_records`
- 再查 `operation_logs where operation_id = ?`
- 再查 `audit_logs where operation_id = ?`
- 如果有 workflow run，再查 `workflow_run_events where operation_id = ? or run_id = ?`

不需要靠时间戳猜。

## 封装组件设计

### 1. OperationScope

新增服务模块，例如：

- `src/server/audit/operationScope.ts`
- `src/server/audit/auditService.ts`
- `src/server/audit/auditTypes.ts`

核心对象：

```ts
type OperationScope = {
  operationId: string;
  log(input: LogEntryInput): Promise<void>;
  audit(input: AuditEntryInput): Promise<void>;
  complete(input?: CompleteOperationInput): Promise<void>;
  fail(error: Error, input?: FailOperationInput): Promise<void>;
};
```

### 2. withOperation

统一入口建议长这样：

```ts
await withOperation(db, {
  sourceKind: 'business',
  domain: 'summary',
  action: 'summary.source.set',
  actor: currentActor,
  entity: { type: 'month', id: monthKey, label: monthKey },
  summary: `Set capitalization source for ${monthKey}`,
}, async (scope, tx) => {
  await scope.log({ eventType: 'operation_started', message: 'Begin setting capitalization source' });
  const before = ...;
  await tx.execute(...主业务更新...);
  const after = ...;
  await scope.audit({
    auditType: 'business_state_change',
    domain: 'summary',
    action: 'summary.source.set',
    entityType: 'month_capitalization_source',
    entityId: monthKey,
    before,
    after,
  });
  await scope.complete();
});
```

这层要负责三件事：

1. 自动创建 `operation_records`
2. 把 `scope.log()` / `scope.audit()` 都绑到同一个事务
3. 自动在异常时写 `operation_failed`

### 3. withWorkflowOperation

workflow 不要直接知道业务表，但可以知道“当前有一个外部 operation context”。

建议 executor / store 接受可选上下文：

```ts
type WorkflowExecutionMeta = {
  operationId?: string;
  requestId?: string | null;
  actorName?: string | null;
};
```

作用：

- `workflowRunStore.createEvent(...)` 写 `workflow_run_events` 时顺带落 `operation_id`
- 如果 workflow 是从业务页面触发，就继承业务页面生成的 `operation_id`
- 如果 workflow 是独立调试触发，就自己新开一个 `operation_id`

### 4. ExcelAuditAdapter

未来如果接入类似 capmerge 的单元格编辑，前端事件不要直接打业务 API，应该走统一适配层：

- `src/client/audit/excelAuditAdapter.ts`
- `src/server/audit/excelOperationRoutes.ts`

前端事件格式可以借 capmerge：

```ts
type ExcelOperationInput = {
  clientOpId: string;
  type: 'cell.update' | 'formula.update' | 'range.paste' | 'row.insert' | ...;
  sheetName: string;
  range: string;
  before?: unknown;
  after?: unknown;
  source: string;
  time: string;
  raw?: unknown;
};
```

但本项目不要直接复刻 capmerge 的 `operations` 表，而是：

- Excel 事件进入后，先映射成 `operation_records + operation_logs + audit_logs`
- 如果未来 Excel 编辑频率非常高，再单独加 `excel_operation_events` 做高吞吐明细表

也就是说：

- Phase 1：统一系统先支持业务动作和 workflow 动作
- Phase 2：如果真的要做单元格级编辑，再加 Excel 专用高频表

## 本项目里的推荐审计粒度

### Phase 1 必须覆盖

这些都是当前已有动作，最值得先接：

1. `POST /api/monthly-runs`
   - 日志：月度执行触发、绑定 workflow、run 创建成功/失败
   - 审计：哪个月、用了哪些 source file、runtime parameters 是什么

2. `POST /api/monthly-runs/:id/approvals`
   - 日志：人工审批进入、提交 decision、workflow 继续执行
   - 审计：谁对哪个 task 做了 approve / reject / continue

3. `PUT /api/months/:month/capitalization-source`
   - 日志：切换 source 开始/完成
   - 审计：before source -> after source

4. `POST /api/files/upload`
   - 日志：上传开始/成功/失败
   - 审计：文件名、checksum、folderPrefix、上传人

5. `PATCH /api/files/:id`
   - 审计：文件重命名 before/after

6. `PUT /api/files/:id/content`
   - 审计：文件内容替换，至少记录 checksum before/after、文件名 before/after

### Phase 2 业务增强

1. workflow definition 编辑、发布、导入、回滚
2. notes 增删改
3. holdings / employees 的批量导入与编辑

### Phase 3 Excel 细粒度

只在项目真正支持在线编辑 workbook 时再做：

1. 单元格改值
2. 公式改动
3. 粘贴范围
4. 行列插删
5. undo / redo

## 与现有 workflow 体系的边界

这个边界需要严格保持：

- `workflow_run_events` 是 workflow 引擎内部运行事件
- `audit_logs` 是业务/Excel/控制面审计
- `operation_logs` 是统一时间线

不要让 workflow 核心去理解：

- 月份页面
- Summary 页面
- 业务展示方式

workflow 核心只做两件事：

1. 正常产出 `workflow_run_events`
2. 如果调用方传了 `operation_id`，就带着这个 id 一起写

业务层负责：

1. 开操作作用域
2. 调 workflow
3. 写业务审计
4. 渲染统一时间线

## 推荐调用模式

### 业务动作

```ts
await withOperation(db, meta, async (scope, tx) => {
  await scope.log({ eventType: 'operation_started', message: '...' });
  const before = ...;
  await ...业务更新...;
  const after = ...;
  await scope.audit({ before, after, ... });
  await scope.complete({ summary: '...' });
});
```

### 触发 workflow

```ts
await withOperation(db, meta, async (scope, tx) => {
  const history = await createMonthlyRunHistory(tx, ...);
  await scope.audit(...history created...);

  const run = await workflowRunStore.createRun({
    workflow,
    tasks,
    runtimeParameters,
    executionMeta: { operationId: scope.operationId, actorName: meta.actor.name },
  });

  await scope.log({
    eventType: 'workflow_run_created',
    message: `Workflow run ${run.id} created`,
    payload: { workflowRunId: run.id },
  });

  await scope.complete();
});
```

### workflow 内部事件

workflow store 继续写 `workflow_run_events`，但多带：

```ts
{
  operation_id: executionMeta?.operationId ?? null
}
```

## 查询与展示

建议未来页面统一走这些查询：

1. 操作列表页
   - 查 `operation_records order by started_at desc`

2. 操作详情页
   - 查 `operation_records where operation_id = ?`
   - 查 `operation_logs where operation_id = ? order by seq asc`
   - 查 `audit_logs where operation_id = ? order by id asc`

3. workflow 运行页
   - 原样查 `workflow_runs + workflow_run_events + workflow_run_approvals`
   - 如果想展示业务侧触发来源，再补查 `operation_records`

4. 业务对象审计页
   - 比如某个月、某个文件、某个 summary source
   - 查 `audit_logs where entity_type = ? and entity_id = ? order by created_at desc`

## 幂等与一致性

### 一致性

必须使用同事务写入：

- 主业务更新
- `operation_logs`
- `audit_logs`
- 必要时 `operation_records.status`

这样不会出现：

- 业务改了，但没审计
- 审计写了，但业务没改

### 幂等

对外部重试敏感的动作建议加业务幂等键：

- `request_id`
- `client_op_id`
- `operation_id`

建议策略：

- 顶层操作允许调用方传 `requestId`
- 若同一个 `requestId + action + entity` 已成功，可直接返回已有 `operation_id`

Excel 细粒度事件则沿用 capmerge 的思路，使用 `client_op_id` 去重。

## 不建议的做法

1. 不要只保留一张 `audit_logs`
   这样既装日志又装审计，最后两边都不好查。

2. 不要让 workflow 层直接写业务审计
   workflow 不该理解 month、summary 页面、业务展示。

3. 不要靠时间戳匹配日志和审计
   必须靠 `operation_id`。

4. 不要把高频 Excel 单元格事件和低频业务动作放在完全相同的表粒度里硬顶
   Phase 1 可以共用统一系统，Phase 3 如果吞吐上来，再单独拆明细表。

## 结论

本项目最合适的方案不是“补强现有 `audit_logs` 一张表”，而是：

- 用 `operation_records` 做顶层操作锚点
- 用 `operation_logs` 做统一时间线
- 用 `audit_logs` 做 before/after 审计
- 用 `workflow_run_events` 保持 workflow 原生运行事件
- 全部通过 `operation_id` 串起来
- 全部通过 `db.transaction(...)` 保证原子性

这样既能覆盖你现在的业务动作，也能为将来的 Excel 细粒度审计留出扩展空间。
